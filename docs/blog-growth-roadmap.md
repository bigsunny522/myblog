## 編集方針案

共通テーマ：**ガジェットと技術で、自分の生活・作業環境を快適にする。**

大学生活、ホワイトデスク、フロントエンド学習、自作ブログという運営者の背景を軸にする。現時点では同じサイト内で次の3分野を扱う案。

| 分野 | 内容 | 既存分野とのつながり |
|---|---|---|
| ガジェット・デスク | 実機レビュー、配置、配線、持ち物、長期使用 | 道具を選んで使う |
| AI活用 | 学習・記事制作・開発で実際に試した結果 | 作業を改善する |
| 開発ノート | 個人開発、ブログ改修、実装、解決した問題 | 自分に必要な道具を作る |

トップの説明文案：

> デスクも、持ち歩きも、使い心地で選ぶ。ガジェットの実体験と、AI・プログラミングで日常を快適にする工夫を紹介します。

カテゴリ追加時はTinaCMS、既存のカテゴリ・タグ運用、一覧・関連記事への影響を確認する。異なる分野の読者が目的の記事へ進める入口を用意する。

## 続けやすい連載と記事候補

新製品の購入や速報追跡に依存せず、実際の改善・学習・使用経験から書く。

| 連載 | 記事候補 |
|---|---|
| デスク改善日記 | 現在のデスクと改善したい3点／配線の困りごとを1つ解決／照明の位置を変えた結果 |
| その後のレビュー | ScreenBarを使い続けて変わった評価／イヤホンを今も使う理由／使わなくなった機能 |
| 大学生のデジタル生活 | 通学バッグの中身／講義日の充電環境／課題に取り組む作業環境 |
| 愛用機器の使い方 | キー配置とショートカット／作業・移動・ゲームでのイヤホンの使い分け |
| AI活用の実験 | 記事制作で助かった工程と書き直した部分／学習でAIの説明をどう検証したか |
| AIとブログを改善する | 課題を選ぶ→実装→確認→残った問題を記録する開発日記 |
| 個人開発ノート | 画像エディタを作った理由／ダッシュボードの設計／MDX運用の利点と不満 |
| 実装・学習記録 | 目次の実装／画像管理の工夫／実際に遭遇したエラーと解決 |

候補は実体験の確認前に完成記事へ変換しない。使用期間、実測値、作業時間、購入理由、失敗談を創作しない。
既存機能は実装を調べてから説明し、「AIで作った」などの制作経緯はユーザーの確認できる事実に基づく。

### 小さな記事の型

1. 何に困っていたか
2. 使用環境と試したこと
3. 結果を示す写真・コード・出力例
4. 良くなった点と残った問題
5. 同じ状況の読者への助言

AI記事は使用ツール・モデル・検証日、入力と出力、修正・検証内容を記録する。公開するプロンプトや画面から個人情報・秘密情報を除く。変わりやすい仕様は執筆時に公式情報を確認する。

小さな経過報告は既存記事の追記にする。異なる読者の疑問に答えられる場合に新記事とし、内容が重複するだけの分割を避ける。

## 継続運営の案

- 月2本を基本案とする：第2週に短い改善・使い方、第4週にレビュー・開発記録・環境紹介。
- 余裕がある月だけイベント記事などを追加。分野は順番に試し、執筆負担と読者の反応を見る。
- `content/ideas/` に「困ったこと／試したこと／結果／写真・コードの有無」を記録する。
- 執筆・公開には既存のテンプレートとワークフローを使う。この記事候補一覧自体は公開対象ではない。

最初の候補は「今のデスク環境と改善したいこと」「既存製品の長期使用」「自作ブログをAIと改善する開発日記」。実際の経験と素材が揃うものから選ぶ。

## レビュー品質の改善

- 冒頭に向く人・良かった点・購入前の注意点を短くまとめる。
- 公称値、実測、主観的な感想を区別する。測定には端末や設置条件を添える。
- Satray記事の「A社」「U社」比較は製品名・型番・出典・比較時点を確認して具体化する。
- 安全性など自分で検証できない説明は、出典と試験条件・適用範囲を明示する。この相談では製品の安全性や全スペックをファクトチェックしたわけではない。
- 既存のPR・当選・アフィリエイトの開示を活かし、評価方針を整える。
- 長期使用で分かったことを追記する。既存記事には目次・購入リンク・関連記事・構造化データがあるため、未実装と扱わない。

## 回遊と計測

まず「現在のデスク環境まとめ」を入口に、ライトやキーボードの個別記事へリンクする案。AI・開発分野も記事が増えたら同様にまとめる。
関連記事は同じ悩み・分野を優先する設計を検討する。

評価指標案：
- Search Consoleの記事別検索クリック数と検索語句。
- まとめ・関連記事へのクリック率（分母と対象を揃えて比較）。
- 記事別の購入リンククリック率。クリックを売上と同一視しない。
- 執筆にかかった時間と継続できた本数。

PR依頼を伸ばす場合は、得意分野・記事実例・レビュー方針をまとめた依頼案内を検討する。優先する事業目標は未確定。

## 90日間の進め方案

- 最初の2週間：サイトマップ、初回演出、日本語表示、計測状況を整理。
- 1か月目：主力レビュー2本を改善し、デスク環境まとめを作る。
- 2か月目：AI・開発を含め月2本程度を試し、関連記事を接続。
- 3か月目：検索語句、クリック、執筆負担を見て次のテーマを調整。

Claude Codeが着手する際は対象項目と現状を確認し、既存のGit・公開ルールに従う。この文書の保存は全項目の実装・記事公開・デプロイの一括指示ではない。実施後は該当項目に日付と変更内容を記録する。
